## Claim and input boundary

`recover.py` accepts exactly one saved Linux x86-64 Firefox core, one complete PCAP, and pinned target metadata. It cannot accept message markers, key logs, server events, workload labels, or target flow assignments. The controlled acquisition and evaluator are separate programs. The evaluator's key logs and connection details lived under a root-only reference directory inaccessible to the unprivileged recovery process; its declared study inputs were staged in a temporary inbox. Case types and donor pairing were root-only during the run. The runner checks both methods' sealed outputs and input hashes before opening the evaluator's answers. The evaluator necessarily reads one reference *before* recovery when constructing the explicit redacted-memory control; that reference is never exposed to recovery.

The environment is Firefox 136.0.2 with the pinned NSS hashes in `capture_blind.py`, Linux x86-64, and `TLS_AES_256_GCM_SHA384`. Resumption, 0-RTT, KeyUpdate, missing handshakes, other systems, and lifetime claims are outside this study.

## Methods

- **Structured:** Imports the existing `rank_tls13.rank` unchanged to enumerate CKA_VALUE candidates, then retains 48-byte candidates for this suite.
- **Entropy:** Reads every 48-byte window in captured ELF load segments in address order, skipping provably ineligible windows inside all-zero pages. It filters at entropy 4 bits/byte and at most six zero bytes, deduplicates values, and keeps the best 100 by entropy and digest.
- **Shared assignment:** Discovers completed TLS 1.3 handshakes and TCP directions from the PCAP. Each candidate is tested against each connection/direction using the normal TLS 1.3 traffic-key derivation and AEAD authentication. A role is selected only if one candidate authenticates at least two application records in a consecutive sequence-zero epoch. A failed, ambiguous, timed-out, or repeated cross-role candidate remains `unresolved`. Payload contents are never inspected for selection.

Both searches receive a 180-second search budget, 300-second record-authentication budget, 100-candidate cap, 16-GiB virtual memory limit, and 540-second CPU limit. The runner alternates method order. Each report records candidate counts, whether search completed, per-role decisions and reasons, wall/CPU time, and peak RSS. The entropy scan's time limit can leave its search incomplete; that outcome is recorded and its candidates found so far are still tested.

## Controlled cases and scoring

The WebSocket workload opens two or three overlapping TLS connections. Each connection sends two varied client messages and receives two varied server messages, with a response between client sends. The server retains its independently generated key log and flow details privately. The evaluator checks that the PCAP contains at least three authenticated application records per direction, accounting for the WebSocket upgrade plus both messages.

The ten-case development pilot has three two-flow and three three-flow positives, one mismatched pair, one unrelated-traffic control, and two redacted-memory controls. The final design has 35 positives of each flow count and ten controls of each type. Mismatched cases receive another fresh case's PCAP; unrelated cases receive PCAPs generated by an independent TLS client. For redacted controls, the evaluator copies the core while preserving its ELF layout and removes every literal occurrence of one target secret, leaving the other target secrets available. These controls are artificial and are reported separately from natural absence in memory.

`run_study.py` creates neutral case IDs and freezes a script snapshot and design manifest. A successful structured-method pilot is required before final freeze; entropy performance is observed but does not gate the pilot. The final uses 600-second start spacing. An attempted case is never replaced. Stage failures stop the campaign for inspection, remain in the denominator, and a later invocation continues only unattempted cases with the same frozen scripts. Raw cores are retained for all cases if pilot maximum core size × 110 images × 1.25 plus a 20-GiB free reserve fits. Otherwise nine case IDs are selected before final results: three per positive group and one per control group. Small PCAPs, hashes, sealed decisions, and scores remain for every case.

The aggregate report counts complete positive recovery, per-target exact recovery, connection/direction assignment, false assignments, correct abstentions, partial recovery, candidate recall, and processing cost. The declared strong-contribution rule is at least 63/70 complete structured positives, zero false assignments across 30 fully scored controls, and a positive paired 95% bootstrap interval for structured minus entropy complete-case recovery with no worse false-assignment rate. The report marks the result as inconclusive if planned cases are unattempted or controls are unscored.

## Running and review

The controlled host needs root for GDB, packet capture, and protected references; recovery runs as `researcher`. After authorized deployment into a **new** source directory beside the existing lab, create a pilot with `run_study.py --study <new-private-study-directory> --create pilot`, then run it with `--run`. Inspect `state.json`, individual sealed outputs, and `summary.json` before freezing a new final directory with `--create final --pilot-summary <successful-pilot-state.json>`. Use the frozen scripts and do not revise a final campaign in place. The pilot and final directories must remain separate from the old 100-case evidence.

Local checks: `python3 -m unittest tests/test_blind_tls13.py` with `cryptography` available, the existing offline tests, and `ruff check lab/blind_tls13 tests/test_blind_tls13.py`. A local sandbox may prohibit socket binding, in which case the controlled-server integration test skips; the pilot must validate the real browser, TLS, PCAP, and isolation path before a final freeze.
